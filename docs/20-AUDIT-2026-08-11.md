## FIXED THIS SESSION

### A1 — the Harvest was mathematically unreachable  ✅ FIXED
`stalker.js`. Notoriety caps at 100. The `absence` band is `[75,100)`, and the
stickiness margin `HYST=3` widens the band a player is *already in* to `[72,103)`.
Since notoriety can never exceed 100, the "am I still in my old band" test could
never come back false, so `absence` was terminal: **the Harvest could not trigger
by play.** Verified before the fix — `resolve(100,'absence') -> 'absence'`.

The whole design ends in the Harvest. It had been unreachable since C6 shipped.

Fix: clamp the widened top to the cap.

```js
var CAP_VALUE = 100   // notoriety's hard ceiling - hysteresis may never exceed it
var hi = Math.min(BANDS[i][2] + HYST, CAP_VALUE)
```

Verified after: `n=100 prev=absence -> harvest`, `n=99 -> absence`,
`n=78 prev=companion -> absence`, `n=74 prev=companion -> companion`. Stickiness
is intact everywhere it was meant to be; only the top is no longer a trap.

### A2 — `/kubejs reload server-scripts` was leaving the server half-dead  ✅ FIXED
`ServerEvents.loaded` **does not re-fire** on that reload. Measured: zero boot
banners across three reloads, so `SERVER` was `null` in the live scope. That
silently disabled the death handler (no Harvest attribution, no XP wipe, no
INVARIANT BREACH alarm) and **the hard stop that stops your own stalker hurting
you**.

I caused this myself by hot-reloading instead of restarting. Two fixes:

* `ensureServer(o)` recovers the handle lazily from any event object, so a
  reload degrades instead of breaking. Called in the death handler, the player
  `beforeHurt` handler, and `flee()`.
* `tools/serverctl.py` now documents the reload as **unsafe for these scripts** —
  the split-brain state (old `scheduleInTicks` chains holding the old `live` map
  while new handlers read an empty one) cannot be repaired from inside a reload.
  **Use a real restart.**

## BROKEN — a whole path has no entry point

### B1 — `mcserver:wall` is unobtainable; the Wall path is dead
Every reinforced block in SecurityCraft bootstraps from a **Universal Block
Reinforcer**, and all three reinforcer recipes are `neoforge:false` stubs in our
own `mcserver_buried_tech`. Machine-checked: of 665 enabled recipes producing a
reinforced result, exactly one takes a non-reinforced input —
`reinforced_crystal_quartz_block` from `block_pocket_wall` — and that is circular
(`block_pocket_wall` is itself crafted from `reinforced_crystal_quartz_block`)
**and disabled by us anyway**.

Also checked and clear: every loot table in all 234 jars, all four buried_tech
loot injectors, `paths.js` Wall drops (keycards, redstone, diamond — no
reinforcer), and `instance/config`. **No source exists.**

Knock-on: the guidebook's Wall "Your First Hour" steps 1–2 name seven items that
are all in the 174 disabled files — keypad, keypad door, keycard reader, camera,
monitor, laser block, retinal scanner.

**Two things I asserted that were false**, both the same error — counting recipes
that *produce* a thing without checking their inputs are reachable:

* `docs/17-PATHS-TO-POWER.md:150-160` — "the Wall is fully craftable today"
* `help.js` Wall hint — "Reinforced blocks are craftable RIGHT NOW - six hundred
  and sixty five recipes." That hint has been telling players a lie since today.

**✅ FIXED, same day** — Ethan chose deep salvage **plus** a path drop, keeping the
buried-tech doctrine (modern tech is found, never crafted):

* `mcserver/loot_table/buried/universal_reinforcer.json` — the item, one roll.
* `mcserver/loot_modifiers/reinforcer_deep_salvage.json` — 10% in abandoned
  mineshafts, stronghold corridor/crossing, Better Dungeons zombie+skeleton, and
  Galosphere forgotten ruins (rare).
* `mcserver/loot_modifiers/reinforcer_ancient_city.json` — 30% in the ancient
  city and its ice box.
* `neoforge/loot_modifiers/global_loot_modifiers.json` with `"replace": false`.
  NeoForge reads **every** copy of that file across all sources — 15 installed
  mods already ship one — so appending is safe and does not clobber theirs.
* `paths.js` — the reinforcer is now in the Wall's **tier-2 and tier-3** drops, so
  the walker is paid one for descending instead of depending on loot rolls. It is
  in both tiers because it is the path's ENTRY item, not a reward for finishing.

lvl2 and lvl3 stay buried. Both false claims corrected: `docs/17` now carries the
correction and names the reasoning error, and the two Wall hints in `help.js` were
rewritten.

Folder naming was verified against the jars before writing, not assumed:
**`loot_table` singular** (3933 instances) and **`loot_modifiers` plural** (68).

## OPEN — KubeJS, ordered by player impact

### K1 + the pumpkin incident — a player was killed by something we spawned  ✅ FIXED

The audit called K1 theoretical ("the Helper has never once worked — zero
`helper answered` in any log, ever"). Restarting for A2 restored `SERVER`, the
Helper fired for the first time, **and it killed someone.** Ethan: *"path of
blade's pumpkin head showed up for half a second, flickered, then summoned a small
minion which promptly killed my brother."* The log: `Lehykt was slain by Senor
Pumpkin`.

Note the sequencing — K1 read as "harmless, it never fires" precisely *because*
A2 had it switched off. Fixing A2 armed it. **A dormant bug is not a mild one.**

Four defects, all in one chain:

1. **The sweep culled the Helper it had just summoned.** `stalker.js` helper
   branch discarded any live stalker, and the sweep runs every 20 ticks — so the
   Helper died about a second after arriving. That is the flicker, exactly as
   described.
2. **So it re-summoned on every hit.** With the Helper culled, `cur` was null on
   the next damage event, so the hook summoned another. The log shows **nine**, at
   `7, 6, 5, 4, 3, 2, 1, 0, -1 hp` — nine boss-tier `lord_pumpkinhead` spawns in
   one fight.
3. **Two of them were summoned for a corpse** (`at 0 hp`, `at -1 hp`).
4. **Culling the parent did not cull its summons.** A stalker removed by
   `dismiss()` left behind anything it had summoned, with no owner relation and no
   idea whose side it was on.

**⚠️ CORRECTION — defect 4 did NOT cause this death.** I first wrote that
`lord_pumpkinhead` summoned the `senor_pumpkin` that killed Lehykt. Checked
against the jar afterwards: **nothing ties Lord Pumpkinhead to Senor Pumpkin.**
The only procedure referencing Senor Pumpkin is *Mrs* Pumpkin's tick handler, and
`senor_pumpkin` ships its own biome modifier — `"biomes": any`, weight 10, count
1–2 — so it is an ordinary ambient mob that spawns everywhere. Lehykt was killed
by a wandering mob while the Helper flickered beside him, and the timing read as
cause. Defects 1–3 are exactly as described and were the real fault.

Defect 4 is still a genuine bug, just not this one's: **Salvage's Hound really
does summon** (`BabySkeleton`, `BoneImp`, `Bonescaller`) and **Wall's Spider
really does summon** (`BloodyGadfly`, `CorpseFly`, `Maggot`). j0nesyboi223 walks
Salvage, so the orphaning was live and reachable — it just had not happened yet.

Fixes, all six anchor-asserted and `node --check` clean:

* `helperLive[uuid]` latches the Helper the damage hook summoned; the sweep now
  skips culling that specific entity and still culls leftover Companions.
* `HELPER_COOLDOWN = 600` (30s) — one visit per cooldown, no summon storm.
* `if (after <= 0) return` — a killing blow does not get a bodyguard.
* `EntityEvents.spawned` (**verified present in the KubeJS jar before use** — this
  codebase has twice been burned by KubeJS silently no-opping an unknown event
  name) tags any living non-stalker mob spawning within `MINION_RADIUS = 12` of a
  live stalker as that stalker's summon. `dismiss()` and the Helper's stay timer
  now call `clearMinions()`, so the parent takes its children with it.

The inference is deliberately narrow: it can only over-collect mobs standing
inside a 12-block ball around a stalker we ourselves placed.

**A second orphaning path, found while re-reading the fix.** `flee()` also removes
a stalker - it is what C5 uses to drive one off at 35% health - and it discarded
the parent without touching the summons, identical failure. `ownerKeyOf()` now
reverse-maps the fleeing entity to its owner and reaps inside the 30-tick retreat
callback, so anything summoned *during* the retreat is caught too. All three
removal paths - `flee`, `dismiss`, the Helper's stay timer - now call
`clearMinions`.

## DECISION NEEDED — how the Wall gets its first reinforcer

The reinforcer is **modern tech**, and the buried-tech doctrine is *modern gear
only as deep salvage*. So the doctrinally right answer is that you **find** one,
not craft one. Routes:

walker. Whichever is chosen, `docs/17` and the `help.js` Wall hint must be

## P1 — the Forge walker was earning NOTHING, silently  ✅ FIXED

Ethan, 2026-08-11: *"i admit this may be a skill issue but mods arent dropping any
of the items they should and i keep dying trying to just get iron."* Neither half
was a skill issue.

**Read from world data, not inferred:**

```
veldora_claim_blade    = "Lehykt"          OK
veldora_claim_salvage  = "j0nesyboi223"    OK
veldora_claim_forge    = ""                <- Rehykt's path
veldora_claim_art      = ""
```

`paths.js` compares the server claim to the killer's name and returns when they
disagree — **no drop, no message, no log line.** Rehykt's playerdata carried
`veldora_path="forge"` against an empty claim, so every monster he killed paid
nothing while the other two were paid normally.

**Cause:** `/path forcerelease` clears the claim but not the holder's own tag.
**And it was unrecoverable in game** — `/path <key>` hits the "you already walk
that path" short-circuit before it would rewrite the claim, so the player is
stuck earning nothing permanently.

**Immediate fix (no restart):** `/path release` then `/path forge`.
**Code fix (staged):** an EMPTY claim now means "unowned", so a player carrying
the tag ADOPTS it and is told so; a claim held by a *real* other name still
refuses, but shouts once per player instead of returning in silence. Cannot
steal — a real holder and escrow are both non-empty.

## P2 — In Control rule order made four rules unreachable  ✅ FIXED (needs /ctrl reload)

20 deaths for Rehykt against 7 / 1 / 1 for the others, to `legendary_monsters`
elites (Resurrected Knight, Beheaded Knight) and `grim_and_bleak:damned_templar`
— mods that rule 10 exists specifically to deny.

Rule 5 was `{"maxlight_sky": 0, "result": "default"}` — *underground, allow
vanilla spawning* — sitting **above** the protective rules. In Control takes the
first matching rule, and every underground spawn has sky light 0, so rules 9, 10,
11 and 12 never ran underground: **no height limit, no mod filter, and the
population cap of 40 never applied.**

Fix: move that rule to LAST. It then only catches what nothing else claimed:

* **y≥40** — no hostiles (rule 9), no Born in Chaos / legendary_monsters /
  grim_and_bleak (rule 10)
* **y0–39** — hostiles allowed, capped at 40 (rule 12)
* **below y0** — unrestricted, which is the intended "the deep is dangerous"

Backups: `spawn.json.prelight.bak` (this) and `spawn.json.preblade.bak` (the
casting deny). In Control does not pick up `/reload`; it needs `/ctrl reload` in
game or a restart.

climbed past the old value. A documented tradeoff that was never re-derived.
